## 11:10 悬停吸附两个真 bug（提交 3d2da01）

- 实测全屏截图（`ImageGrab.grab(all_screens=True)`，虚拟桌面 3840x1200）：

## 12:10 macOS 端补齐（提交 f86590c）

### ① 窗口吸附在 mac 上原本是空桩 → 真实现（winsnap_mac.rs）
用 `CGWindowListCopyWindowInfo(kCGWindowListOptionOnScreenOnly|ExcludeDesktop, 0)`：
- **返回数组本身就是 z 序（最上层在前）**，命中第一个即止 —— 不需要 Windows
  那套 GetAncestor + GW_HWND 回溯
- 过滤 `kCGWindowLayer == 0`（排除菜单栏/Dock/浮动面板/输入法候选框）
- 跳过浮层自己：按 `kCGWindowNumber`（用 `objc_msgSend(ns_window, sel"windowNumber")`
  从 Tauri 的 `ns_window()` 拿）；拿不到号时**保守跳过本进程全部窗口**
- 标题 `kCGWindowName`，空则退回 `kCGWindowOwnerName`
- **必须 CFRelease** 返回数组（15fps 查询，不释放会持续漏）
- **坐标是"点"**：屏幕点 = 显示器原点 + 浮层内坐标，**不乘 scale_factor**
  （Windows 才要乘）。这两套单位差异在 winsnap.rs / commands.rs 都写了注释

### ② 关键工程手法：让 macOS 代码能在 Windows 机器上验证
`winsnap_mac.rs` 刻意**不依赖父模块类型**（返回自己的 MacWindow），于是可以：
`rustc --emit=metadata --target aarch64-apple-darwin --crate-type lib winsnap_mac.rs`
→ 不需要链接器/SDK，就能在 Windows 上做类型检查（cargo check --target 会卡在
objc2-exception-helper 需要 macOS 的 cc）。**本机已验证 exit 0**。
aarch64-apple-darwin 的 std 在 **1.98.0 工具链**里（不在 stable）。

### ③ 默认热键按平台
mac 默认 `Super+1/2`（⌘），win 默认 `Ctrl+1/2`；config.rs 的 DEFAULT_* 常量
与 lib.rs 的 default_*_shortcut() 必须同步改（否则"解析失败回退默认"与 UI 不一致）。
前端 MainWindow 加 IS_MAC + prettyKey()（⌘⌥⌃⇧ 显示），"恢复默认"按钮不再写死 Ctrl。

### 仍待 mac 真机验证
- CGWindowList 的 `kCGWindowName` 需要屏幕录制权限（应用本来就要，应该没问题）
- mac 上默认热键改成了 ⌘1，老用户 config.json 里存的是 Ctrl+1 → 保持不变（不做迁移）

## 10-25 05:40 设置窗口关不掉（真因：缺 allow-destroy 权限）
**Tauri v2 的 JS `onCloseRequested` 在"不调 preventDefault"时会内部 `destroy()`**，
而 capabilities 只给了 `core:window:allow-close`、没给 `allow-destroy`
→ destroy 被 ACL 静默拒绝 → 窗口永不关闭（点 ✕/Alt+F4 全无反应）。
诊断手法：用 PostMessage(WM_CLOSE) 触发原生关闭 + 日志打印 error，
直接看到 `destroy not allowed by ACL`。**以后任何"窗口关不掉"先查 ACL。**
另修：关闭确认从"5 秒内再点一次"改为持久态 + 视口底部固定提示条
（旧提示印在页面底部状态栏，设置页要滚动才看得到 → 用户以为没反应）。

## 10-27 17:00 0.1.11：辅助功能授权「怎么点都无效」的真因 = 浮层把系统设置挡住

**0.1.10 真机日志（5 次启动）实证**：
- 屏幕录制 preflight 第 3 次启动起 = true（走系统弹窗授权的，成功）；
- 「辅助功能」4 次全 false，`long capture blocked: 无「辅助功能」权限`；
- `reset perms: screen=Ok access=Ok` 执行成功 → tccutil 可用。

**推断（依据代码，非真机复现）**：浮层是**全屏 + always_on_top 的不透明冻结图**
（windows.rs `.always_on_top(true)`），而辅助功能只能靠人手动去系统设置里勾。
`accessibility_hint` 弹框里的「打开系统设置」→ 系统设置窗口被全屏置顶浮层整块盖住，
用户什么都看不到/点不到 ⇒ 两版日志里 AXIsProcessTrusted 一直是 false。
屏幕录制能成，恰恰是因为它走**系统弹窗**，系统弹窗永远在最上层。

**0.1.11 修法**：
1. 缺权限时先 `overlay.set_always_on_top(false)` 再开系统设置（授权成功那一路再置顶）；
2. 不再 `return Err`（Err 只到前端 console，浮层永远停在"正在启动…"）→
   发 `phase="need-accessibility"`，UI 切 blocked 卡片；
3. 卡片 800ms 轮询 `accessibility_granted`，勾上**自动重跑**（辅助功能是即时生效的，
   **不需要重启应用** —— 之前提示"然后重启应用"是错的，白白浪费重启）；
4. 卡片三出口：打开系统设置 / 重置授权（tccutil reset Accessibility + 立刻重新
   prompt，把僵尸条目重新加回列表）/ 我已授权重试；
5. 会话泄漏自愈：`long` 有值但 `long_active=false` → 直接丢弃（0.1.10 的待办）；
6. 补提交 `vite.config.ts` 的 `longresult` 入口 —— 0.1.10 **漏提交**了，CI 出的包
   结果窗会 404 白屏（本地 build 用的是工作区里未提交的配置，所以本地测不出来）。

**坑**：GitHub 侧 `main` 上的提交是上一轮用 Data API 造的（SHA 与本地不同，内容相同），
`git push` 会 non-fast-forward。用 `git merge -s ours origin/main` 造合并提交再推，
不要 force push。探测：`git diff --stat origin/main HEAD` 只应出现自己改的文件。

## 10-27 17:15 0.1.12：macOS「点长截图就闪退」的排查与嫌疑摘除

**用户反馈**：0.1.10 上点长截图直接闪退。**日志实证**：
- 两次点长截图，日志都在 `long capture blocked: 无「辅助功能」权限` 这一行之后
  立刻 EOF（后面是用户手动重开应用的新 `===== start =====`）；
- `logfile.rs` 的 `write_line` **每行 flush**，且 macOS 下 stderr 已 `dup2` 到同一个
  日志文件 → 若发生 Rust panic，panic 消息会落盘。日志里**没有 panic** ⇒ 不是
  panic（unwind 也不会带走进程），是**原生信号级崩溃**或被强杀；
- 该路径顺序是：log → `accessibility_hint` → 里面第一个原生调用就是
  `AXIsProcessTrustedWithOptions`（手搓 CFDictionary）→ 然后才弹框。
  同机已证安全：`AXIsProcessTrusted()`（5 次启动都正常）、`tccutil`、`open` 子进程。

**顺带发现的老 bug**：`CFDictionaryCreate` 传了 NULL 的 key/value callbacks →
字典按**指针身份**比较 key，`AXIsProcessTrustedWithOptions` 内部用
`CFSTR("AXTrustedCheckOptionPrompt")` 查表永远查不到 ⇒ prompt:true 一直退化成
纯查询，"系统授权框从来没弹过"。也就是说这条调用**本来就没起作用**，摘掉不损失功能。

**0.1.12 处理**：
1. 被拦路径不再调 prompt FFI，只 `open` 系统设置面板；
2. `set_always_on_top` 一律投主线程（`run_on_main_thread`）：NSWindow level 不能在
   异步命令的工作线程上改（0.1.11 新加的那两处是潜在崩溃点）；
3. 被拦路径逐步打日志（1/2 打开面板 → 2/2 已请求 → need-accessibility 已发）
   + 线程 3 秒后打 `alive 3s after block` 心跳。下次若还崩，日志能精确停在哪个动作；
4. 核心层 `request_accessibility_permission` 保留但修好 callbacks（kCFType*），
   注明"已从热路径摘掉，等 .ips 再决定是否恢复"。

**下一步需要用户给**：`~/Library/Logs/DiagnosticReports/SnapPin-*.ips`（崩溃报告），
里面有 Faulting Thread 的符号栈，能直接确认真凶。

## 10-27 21:50 0.1.10 闪退 **确诊**（.ips 到手）+ 长截图滚不动（0.1.13）

**崩溃报告给出铁证**（用户给的两份 .ips，app_version 0.1.10，faultingThread=3 名
`tokio-rt-worker`）：
```
exception: EXC_BAD_ACCESS (SIGSEGV) KERN_INVALID_ADDRESS at 0x8
CoreFoundation   CFGetTypeID + 10
HIServices       AXIsProcessTrustedWithOptions + 121
SnapPin          <我们的帧>
```
⇒ 崩在 `AXIsProcessTrustedWithOptions`，它内部对字典取出的 value 做
`CFGetTypeID(v)`，而 v 是 NULL（读 `((void*)0)->isa` 附近的 0x8）。

**完整根因链**：`CFDictionaryCreate` 传了 NULL 的 key/value callbacks →
字典按**指针身份**比较 key → 系统用 `CFSTR("AXTrustedCheckOptionPrompt")` 常量
查表**永远查不到** → value=NULL → Apple 的实现没判空就 `CFGetTypeID(NULL)` → SIGSEGV。
所以这个"弹系统授权框"的调用从 0.1.7 起既没生效、又会崩，只是没人走到过。

**0.1.12 真机验证通过**（日志 snappin(5).log）：
- 不再闪退；`blocked: 1/2 → overlay lowered → 2/2 → need-accessibility`
  → `alive 3s after block` → 用户勾选后 **自动继续**，`辅助功能权限 = true`；
- 长截图跑到结果窗、`long commit(save) start: 3360x1850`，保存成功；
- `.ips` 里 `codeSigningID=com.snappin.dev`、`codeSigningTeamID=""`（adhoc），
  但 TCC 授权能持久生效 —— 说明 adhoc 不是障碍，之前"权限怎么点都没用"纯粹是
  浮层挡住系统设置 + 这个崩溃把人吓跑。

**新问题（0.1.13 修）**：三次长截图都只有 `1850px`（= 选区高度 925pt×2），
一步没拼上；事件确实 post 出去了（否则 `scroll_wheel` 会 Err）。
推断：`CGEventCreateScrollWheelEvent(kCGScrollEventUnitLine)` 只填 **line delta**，
而 Chromium/WebKit 读 **point delta**（NSEvent.scrollingDeltaY）→ 视为 0px。
改：单位改 pixel，显式写 point/fixed-point/line 三个 delta，并
`kCGScrollWheelEventIsContinuous=1` 逼浏览器走 precise 分支（line 分支已实证无效）。
字段号：DeltaAxis1=11、FixedPtDeltaAxis1=93、PointDeltaAxis1=96、IsContinuous=88。
驱动循环每步落一行 `long step N: kind/score/height/light`，下次能区分
"没滚"（Still+height 不变）与"滚了但拼不上"（NoMatch）。
若 0.1.13 仍不滚，下一步是 `CGEventPostToPid`（直接投给光标下窗口的 PID）。
